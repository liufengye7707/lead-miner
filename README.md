# B2B 销售商机挖掘 Skill｜中文使用说明

这不是一份“客户百科”，而是一位销售在拜访前用来做判断的工具：**我手上的产品，能不能卖给这个客户；从哪个小场景切入；找谁；什么时候找；要避开什么竞争或合作风险。**

它只使用互联网上人人都能正常打开的公开信息，并且会为关键事实附上来源、日期和链接。它不会使用登录后数据、隐私数据、泄露数据，或绕过网站限制获取的信息。

## 你只要这样提问

把下面两项发给 Skill：

```text
客户：公司全称
我想卖的产品：产品名称 / 方案名称
```

如果你愿意，额外补充下面任一项，结果会更准：

```text
我方角色：云厂商 / 软件厂商 / 集成商 / 渠道伙伴
产品资料：官网链接或一句产品能力说明
已知关系：我方已有联系人、已知供应商、已有合作线索
本次目标：首次拜访 / 找试点 / 续约 / 联合打单
拜访对象与日期：例如 CIO、业务负责人、采购负责人
```

示例：

```text
客户：大众汽车金融（中国）有限公司
我想卖的产品：企业知识库和智能问答平台
我方角色：软件厂商
本次目标：争取一次 30 分钟的业务与 IT 联合沟通
```

## 它会给你什么

| 你真正关心的问题 | 输出会怎样回答 |
| --- | --- |
| 这家公司能不能卖？ | 明确给出：可推进 / 有条件推进 / 长期培育 / 联合伙伴切入 / 暂不建议，并说明把握度。 |
| 从哪里切入？ | 不只说“可以用 AI”，而是写清楚：客户公开在做什么 → 产生什么麻烦 → 产品能先解决哪一步 → 需要向客户确认什么。 |
| 找谁？ | 按业务、IT/研发、安全合规、采购、生态伙伴等角色，说明各自关心什么、首要目标是什么。 |
| 什么时间找？ | 把财报、预算、招标、系统上线、监管审计、业务旺季等节点整理成商机日历。 |
| 有谁在里面？ | 区分已被公开证实的供应商、集团层面的关系、市场竞品、尚待核实的线索，避免把猜测当事实。 |
| 有哪些竞争风险？ | 只比较同一产品层的替代方案，给出“正面竞争、增量切入、联合交付、仅战略推进、避免”的建议。 |
| 第一次怎么聊？ | 给出有公开新闻佐证的破冰话术、可问的问题和下一步小动作。 |

## 怎么看输出：先看这四块

### 1. 结论卡：先判断值不值得花时间

开头的结论不是“客户很好”，而是销售动作建议。

- **可推进**：公开证据已表明有较强的业务场景和时点，可以约关键人、推进试点。
- **有条件推进**：有机会，但还差一个关键事实，例如客户是否已有同类系统、数据能否使用、谁有预算。
- **长期培育**：方向合理但时点不成熟，先建立关系、持续输入行业信息。
- **联合伙伴切入**：客户可能更适合由其现有集成商、软件商、咨询商一起进入。
- **暂不建议**：对方可能是直接竞争者，或产品层高度冲突、风险大于收益。

**“成功概率/得分”是基于公开证据的销售判断，不是客户已经承诺的成交概率。**

### 2. 场景链：防止“看行业就硬推产品”

每一个推荐场景都必须走完这条链：

```text
公开事实
→ 客户正在做的事情
→ 由此产生的压力
→ 产品能先进入的具体环节
→ 下一次需要向客户确认的问题
```

例如，不能因为一家银行属于金融行业，就直接断言它“需要大模型”。更好的说法是：

```text
公开事实：客户正在扩张线上服务或发布某项数字化产品
→ 工作流：客服、运营、研发或风控团队需要处理更多重复信息
→ 压力：人工查询慢、培训成本高、审查要求严格
→ 切入点：先做带引用来源、人工审核、权限控制的内部知识问答试点
→ 待确认：现有知识库在哪、哪些部门可先试、是否已有同类供应商
```

### 3. 供应商与竞品：别把“听说”当作“已合作”

报告会把关系分开标注：

- **客户已合作供应商**：有客户官方、招标、双方联合公告等公开证据。
- **集团层面关系**：母公司或关联公司合作过，但不能直接等同于本客户也在使用。
- **市场竞品**：同行常见方案或我方可能遇到的对手，不代表已经进入客户。
- **待核实线索**：招聘描述、合作伙伴案例、媒体提及等，只能作为拜访时的问题，不能当成事实。

每条证据都有可信度：

| 级别 | 用大白话解释 |
| --- | --- |
| A | 客户自己、监管机构、交易所或政府公开说过，最可靠。 |
| B | 供应商官方或双方联合宣布过，较可靠。 |
| C | 权威媒体或行业组织报道，可做线索但要交叉验证。 |
| D | 只能提示方向，不能作为销售结论。 |

### 4. 销售行动：把“大项目”拆成一个能开始的小动作

报告会建议一个试点，而不是空泛地建议“推进合作”。试点会写清：

- 用哪个产品，解决哪个工作流；
- 哪些范围暂时不碰，例如核心交易、生产核心系统、敏感数据；
- 先找哪个部门和角色；
- 预计用多长时间；
- 用哪些指标判断试点有没有价值；
- 试点成功后，下一步如何扩大。

常见的衡量方式包括：人工查询时间、重复步骤减少量、使用人数、答案引用率、人工审核通过率、交付周期、作业成功率等。它们是**建议目标**，不是客户已经给出的数据。

## 分数是怎么来的

总分 100 分，用来帮助排优先级：

| 维度 | 权重 | 大白话 |
| --- | ---: | --- |
| 产品和需求匹配 | 25 | 产品是否真的能解决客户当前问题。 |
| 工作流/痛点证据 | 20 | 有没有公开事实证明这个问题正在发生。 |
| 战略关系与竞合风险 | 20 | 客户是终端、伙伴还是竞争者；会不会有冲突。 |
| 预算与时点 | 15 | 是否临近预算、招标、上线、续约或业务关键节点。 |
| 关键人可触达性 | 10 | 是否能识别出需要找的业务、IT、采购或合规角色。 |
| 竞争可赢性 | 5 | 是否有可验证的差异化，或适合联合进入。 |
| 交付/安全/合规可行性 | 5 | 是否适合从一个低风险、可审计的范围起步。 |

分数解释：80–100 优先投入；60–79 有条件追；40–59 先培育或试点；低于 40 暂缓或仅战略维护。若客户是直接竞争者，关系判断会优先于分数。

## 三个最容易犯的错误

1. **把行业共性当成客户需求。** 行业里常见，不代表这家公司此刻就在买；必须有公开证据或客户确认。
2. **把集团合作当成客户合作。** 母公司用了某厂商，不等于子公司、分公司或指定法人主体也在用。
3. **拿不相同的产品硬比较。** 办公工具、行业应用、模型平台、算力和交付服务不是同一层，只有同层替代才适合横向比拼。

## 文件说明

| 文件 | 什么时候需要看 | 它的作用 |
| --- | --- | --- |
| `SKILL.md` | 你想知道 Skill 的总规则时 | 核心说明：输入什么、必须输出什么、公开信息边界和整体流程。 |
| `decision-framework.md` | 你要判断能否卖、怎么赢、怎么做试点时 | 销售决策、竞合关系、供应商地图、评分、试点和报告模板。 |
| `signals-and-visit.md` | 你要做商机追踪、找拜访话题和时间节点时 | 按行业自适应抓五类信号、新闻优先级、商机日历和破冰话术。 |
| `openai.yaml` | 一般不需要看 | 给 Codex 界面识别和展示这个 Skill 用的配置文件。 |

## 一句话记住

输入“客户 + 产品”，它会用可核验的公开信息告诉你：**能不能卖、卖给谁、从哪里开始、什么时候行动、有哪些对手或伙伴，以及下一步最小的销售动作。**
